## Why this change
G267 internal alternative introduced a distinct optional `REVIEW_DUPLICATES` mode via catalog `ug-filemgr scan-dedupe`. Its action is published as read-effect, but has no documented `limit` or `max-depth` arguments; when scope enforcement cannot be proven the Skill correctly stops with `NOT_CHECKED`. That means a user could have no practical bounded duplicate review even when willing to approve a handful of exact documents. G268 adds a new *explicitly opt-in and non-automatic* alternative using registered `file-agent` and the actually listed `ug-filesystem find` and `ug-filesystem sha256sum` read-only actions. No vendor runtime invocation occurred.

**Architecture trade-off:** A) keep `scan-dedupe` as the only candidate path: fewer instructions and requests, but unknown recursion and unbounded operation. B) after the original scan refuses, ask for a distinct owner-approved max-40-document comparison: published `find` supports `type=documents`, `max-depth`, `limit`; `sha256sum` requires one exact path and read-effect. B selected as a separate consented *proposed* path. Higher per-file action count (max 40) but bounded size, no new paid API or Python on Uliya NAS. Catalog provides parameters but does NOT prove device registration, depth semantics, effective permission, data-locality or completion.
